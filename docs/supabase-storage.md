# Supabase Storage — media pipeline setup

Owner: Agent 4 (media layer). Companion to `docs/backend-setup.md` (Firebase) — this file covers
only the image bucket and the bookkeeping around it.

> **Nothing in this document has been executed against a live Supabase project.** It is written from
> the code in `lib/app/core/services/media/` and the storage policies that code expects. Every
> `<ANGLE_BRACKET>` value is a placeholder to substitute; there are deliberately no real project
> urls, keys or tokens in this repo, and the pipeline refuses to run without them.

---

## 1. The one rule that shapes everything

The browser holds only the **publishable (anon) key**. That key grants no privilege of its own:
every read and write below is authorised by a Postgres **RLS policy** on `storage.objects`, scoped
to the `anon` / `authenticated` role and, for writes, to the object key prefix and the uploader's
own `auth.uid()`.

Consequences:

* `SUPABASE_SERVICE_ROLE_KEY` must **never** reach the Flutter bundle. `Env`
  (`lib/app/core/env.dart:28`, `:37`) reads that define solely to assert it is absent;
  `hasServiceRoleKeyInClient` is checked by `AppBootstrap`. The key lives in Firebase Functions
  config (`functions/.env`, gitignored) for the cleanup job in §8.
* A client-side "is this admin?" check (`MediaConfig.canManageMedia`) is UX. Deleting a policy or
  shipping a modified bundle cannot delete anyone's images, because the policy has the last word.
* All placeholders in this file are of the form `https://<PROJECT_REF>.supabase.co` and
  `sb_publishable_…`-style descriptions — never a plausible-looking credential.

## 2. Build-time client configuration

```bash
fvm flutter build web --release \
  --dart-define=SUPABASE_URL=https://<PROJECT_REF>.supabase.co \
  --dart-define=SUPABASE_ANON_KEY=<PUBLISHABLE_KEY_FROM_DASHBOARD> \
  --dart-define=SUPABASE_MEDIA_BUCKET=om-events-media
```

| Define | Required | Read by |
| --- | --- | --- |
| `SUPABASE_URL` | yes | `Env.supabaseUrl` → `AppBootstrap` (`Supabase.initialize`) |
| `SUPABASE_ANON_KEY` | yes | `Env.supabaseAnonKey` (publishable/anon — the same public client credential) |
| `SUPABASE_MEDIA_BUCKET` | no, defaults to `om-events-media` | `MediaConfig.bucket` |

**Honest failure states.** `MediaConfig.availability` distinguishes them, and the wording is what an
operator sees in the admin panel (`OmMediaStorageNotice`):

| State | Message | Fix |
| --- | --- | --- |
| keys absent | `Media storage is not configured: SUPABASE_URL and SUPABASE_ANON_KEY must be supplied with --dart-define.` | add the defines |
| keys present, `Supabase.initialize()` failed | `Media storage is offline because Supabase failed to initialise (…)` | check the url/role key pair |
| Supabase up, Firebase absent | uploads throw `Cannot record the upload — FIREBASE_* must be supplied with --dart-define.` | an unbookkept object is undeletable, so the pipeline refuses to upload rather than leak bytes |

Every `MediaRepository` method on an unconfigured build **throws**
(`UnconfiguredMediaRepository`, `lib/app/bindings/media_binding.dart:35`); nothing returns an empty
success, and no repository is ever a no-op.

## 3. Create the bucket

Dashboard → Storage → New bucket, or:

```bash
supabase projects api-keys                 # sanity check which project you are pointed at
supabase storage create om-events-media --public --file-size-limit 8MiB
```

Settings the code assumes (`lib/app/core/services/media/media_limits.dart`):

| Setting | Value | Why |
| --- | --- | --- |
| Public read | **your choice** — both modes are supported | §5 explains what changes |
| Max file size | 8 MiB | highest `MediaKindRules.maxBytes` (product/banner) is 8 MiB; a larger bucket limit is pointless, a smaller one makes the client cap a lie |
| Allowed MIME types | `image/jpeg`, `image/png`, `image/webp`, `image/avif` | mirrors `MediaLimits.allowedMimeTypes`. No SVG (script-carrying, same origin), no GIF/HEIC/BMP/TIFF |
| Enable image transformations | **on** | `MediaRef.thumbnailUrl` and `MediaRenderSize` depend on `/render/image` |

`getBucket()` is read once at run time (`SupabaseStorageService.resolveVisibility`,
`supabase_storage_service.dart:169`). If the anonymous role cannot read the bucket row the pipeline
assumes *public* and logs it — storing an expiring signed URL in Firestore is the more expensive
mistake, so it errs away from that. Grant `SELECT` on `storage.buckets` (see §4) to remove the guess.

## 4. RLS policies on `storage.objects`

Object keys are generated by `MediaPathPolicy` — `{folder}/{entityKey}/{order:3}-{mediaId}.{ext}`,
with unattached uploads at `tmp/{writerUid}/{mediaId}.{ext}`. `mediaId` is a 16-character token from
`Random.secure()` (`media_id.dart`), so keys are unguessable and a retry always overwrites its own
key instead of creating a second copy. Only `[a-z0-9-]` (slugified entity segment) and
`[a-z0-9]` (extension, ≤5 chars) survive sanitisation, so no `../` or `/` can be smuggled in through
a product slug or a file name.

Because the stage lives in the **path**, one policy per prefix does the whole authorisation job:

```sql
-- 0. Turn RLS on. Supabase enables it by default for storage.objects; assert it anyway.
alter table storage.objects enable row level security;

-- 1. Read: only needed for a PRIVATE bucket (a public bucket serves /object/public/… without a
--    policy). Allow any visitor to read final objects, and nobody to read another writer's staging.
create policy "om media public read final objects"
  on storage.objects for select
  to anon, authenticated
  using (
    bucket_id = 'om-events-media'
    and split_part(name, '/', 1) in ('products', 'categories', 'banners', 'misc')
  );

-- 2. Staff write: final prefixes are restricted to the authenticated role.
--    Replace <STAFF_ROLE_CLAIM> with how your staff are identified in the Supabase JWT
--    (a `app_metadata.role` claim is the usual one — see the note below).
create policy "om media staff write final objects"
  on storage.objects for insert
  to authenticated
  with check (
    bucket_id = 'om-events-media'
    and split_part(name, '/', 1) in ('products', 'categories', 'banners', 'misc')
    and exists (
      select 1 from auth.users u
      where u.id = (select auth.uid())
        and u.raw_app_meta_data ->> 'role' = 'admin'   -- <STAFF_ROLE_CLAIM>
    )
  );

create policy "om media staff overwrite final objects"
  on storage.objects for update
  to authenticated
  using (bucket_id = 'om-events-media'
         and split_part(name, '/', 1) in ('products', 'categories', 'banners', 'misc'))
  with check (bucket_id = 'om-events-media'
              and split_part(name, '/', 1) in ('products', 'categories', 'banners', 'misc'));

create policy "om media staff delete final objects"
  on storage.objects for delete
  to authenticated
  using (
    bucket_id = 'om-events-media'
    and split_part(name, '/', 1) in ('products', 'categories', 'banners', 'misc')
    and exists (
      select 1 from auth.users u
      where u.id = (select auth.uid())
        and u.raw_app_meta_data ->> 'role' = 'admin'   -- <STAFF_ROLE_CLAIM>
    )
  );

-- 3. Anyone with a session may stage and promote inside their OWN tmp/ prefix.
--    The first path segment after tmp/ is auth.uid(), which is the only subject RLS can verify,
--    so it is what `SupabaseStorageService.writerUid()` puts in the key (NOT the Firebase uid).
create policy "om media own staging insert"
  on storage.objects for insert
  to authenticated, anon
  with check (
    bucket_id = 'om-events-media'
    and split_part(name, '/', 1) = 'tmp'
    and split_part(name, '/', 2) = (select auth.uid())::text
  );

create policy "om media own staging select"
  on storage.objects for select
  to authenticated, anon
  using (
    bucket_id = 'om-events-media'
    and split_part(name, '/', 1) = 'tmp'
    and split_part(name, '/', 2) = (select auth.uid())::text
  );

-- 4. Customer review photos: the writer owns the object; the app moves it into reviews/ and the
--    moderation rule (not this policy) governs who may then delete it.
create policy "om media own review insert"
  on storage.objects for insert
  to authenticated
  with check (
    bucket_id = 'om-events-media'
    and split_part(name, '/', 1) = 'reviews'
    and split_part(name, '/', 2) = (select auth.uid())::text
  );

create policy "om media own review delete"
  on storage.objects for delete
  to authenticated
  using (
    bucket_id = 'om-events-media'
    and split_part(name, '/', 1) = 'reviews'
    and (
      split_part(name, '/', 2) = (select auth.uid())::text
      or exists (
        select 1 from auth.users u
        where u.id = (select auth.uid())
          and u.raw_app_meta_data ->> 'role' = 'admin'   -- <STAFF_ROLE_CLAIM>
      )
    )
  );
```

Notes that change behaviour if skipped:

* **Promotion needs `INSERT` + `DELETE` on the destination/source**, because
  `objects.move()` (`media_uploader.dart:545`) is a server-side rename: policy 2's `insert` and
  policy 3's staging delete cover it. Grant staging delete with
  `"om media own staging delete"` mirroring policy 3's `using` clause if you prefer explicit
  statements over the `update` policy above.
* **`bucket_id` must be in every clause.** Without it a policy leaks the other buckets in the
  project.
* **`getBucket`/`buckets` read**: `resolveVisibility()` calls `storage.getBucket()`. Grant staff
  `select` on `storage.buckets` for `bucket_id = 'om-events-media'`, or accept the logged
  "assuming public URLs" fallback.
* Supabase's built-in `storage.objects` owner column is set to `auth.uid()` on upload; if you would
  rather policy on `owner` than on the key prefix, keep the prefix rules as well — the pipeline's
  paths are the thing the client can reason about.
* `media_objects` (the Firestore ledger) is a different system: its rules belong to
  `firestore.rules` and are covered in `docs/backend-setup.md`.

### 4.1 A session must exist

`writerUid()` (`supabase_storage_service.dart:126`) uses the current Supabase user and, if there is
none, calls `auth.signInAnonymously()`. So either:

* enable **Allow Anonymous Sign-Ins** (Auth → Providers) — uploads then work for a signed-out
  operator, each landing in its own `tmp/<uuid>/`; or
* exchange the Firebase ID token for a Supabase session for staff
  (`supabase.auth.setSession` with a custom token minted by a Cloud Function). Recommended for
  production: policy 2's `role = 'admin'` claim is then meaningful.

Without either, uploads fail with a message naming the setting to change — never silently.

## 5. What gets stored where (the signed-URL rule)

**A signed URL is not a storable value.** It is a read grant that expires; persisting one into a
product document produces an image that breaks at 03:00 and looks like deleted media.

| | Public bucket | Private bucket |
| --- | --- | --- |
| `MediaRef.url` | permanent `https://<PROJECT_REF>.supabase.co/render/image/public/{path}?width=…` (or `/object/public/…` unstored) | **empty string** — there is nothing permanent to write |
| `MediaRef.storagePath` | the object key — this is the real stored value | same |
| Render-time URL | derived locally from `storagePath` + size | `createSignedUrl`, cached |
| Cache | `SignedUrlCache` unused | TTL 15 min, re-signed 3 min before expiry |

`MediaRefResolver.urlFor` (`media_ref_resolver.dart:50`) is the only place a display URL is produced,
and `MediaUploader._refFor` (`media_uploader.dart:579`) is the only place a stored URL is written —
it writes `''` when the bucket is private. Any reference whose URL already carries `token=` is
re-signed, not trusted, so documents written by an older build cannot serve a stale grant.

Caching is per-transform (`signedUrlCache` vs `thumbnailCache`, `supabase_storage_service.dart:71-83`)
because a signed URL embeds the transform in its signature: one path legitimately has two different
signed URLs, and sharing one map would make a grid download originals under a thumbnail's name.
Concurrent requests for the same path share one in-flight signature.

Callers must obtain URLs through `MediaUploadPipeline.resolveForRender(...)` immediately before
rendering — see §7 for the storefront consequence.

## 6. Transformations, CDN and cache headers

Sizes come from `MediaLimits` and are single-sourced so the docs, the validator and the UI cannot
drift:

| Purpose | URL form | Code |
| --- | --- | --- |
| Grid/card | `/render/image/public/{path}?width=480&resize=cover&quality=80` | `MediaLimits.thumbnailWidth`, `thumbnailUrl()`, `MediaRef.thumbnailUrl` |
| Detail hero | `…?width=1600&resize=cover&quality=85` | `heroWidth`, `heroUrl()` |
| Original | `/object/public/{path}` | `publicUrl(path)` |

`OmMediaImage` decodes grid images at 480px (`cacheWidth`), which is why `MediaRef.thumbnailUrl`
appends `width=480` when a stored URL has no query string — the two must agree or the browser
resamples a full-size file on a phone.

Cache-control written on upload (`media_uploader.dart`):

* final objects: `86400` (24 h). Not `immutable`: `replace()` overwrites the key **in place** so no
  document can ever point at a deleted object — which also means the CDN edge can serve the old
  bytes for up to 24 h.
* staged objects: `300` (5 min) — dead bytes should not live long.

**Purge requires the management API** (`POST /auth/v1/admin/…`/`/storage/v1/object/cdn/{bucket}/{path}`),
i.e. the service-role key, so it is a Functions/ops action and never a browser one. Until someone
runs it, the admin sees the `debugPrint` note "the CDN edge may serve the old bytes for up to 24h
without a purge" (`media_uploader.dart:406`). If a "my image did not change" ticket arrives, it is
this, not the pipeline. A cache-busting `cacheNonce` on the render URL is the low-cost alternative
the storefront can use.

## 7. Lifecycle of one upload

```
pick bytes
  → MediaValidator.analyse()          mime + magic bytes + byte cap + pixel bounds + alt text + cap
  → media_objects row (state=staging)  written BEFORE any byte leaves the browser
  → tmp/{writerUid}/{mediaId}.{ext}    uploadBinary(upsert: true)
  → [optional mediaOptimise function]  §9
  → move(tmp → {folder}/{entityKey}/{order:3}-{mediaId}.{ext})
  → media_objects row (state=attached) upsert on the same id
  → MediaRef returned
```

* **Validate before transfer.** Nothing in this sequence transfers bytes before
  `MediaValidator.analyse` accepts them; a rejected file costs the admin one toast, not an object,
  a CDN entry and a mystery. `MediaRepository.validate()` is the context-free pre-flight the admin
  form calls first, and it uses the loosest byte cap because the interface signature carries no
  `MediaKind`.
* **Cancel** sets the flag, stops the SDK's retry loop through `StorageRetryController`, removes the
  staged object and detaches the ledger row. If the object had already been promoted, the attempt
  legitimately completes — a publish that happened is not reported as a lie.
* **Failure after promotion** now rolls back: `_rollbackPromoted` (`media_uploader.dart`) deletes the
  promoted key when the ledger does not report it `attached`, because those bytes would otherwise be
  stranded outside the `tmp/` expiry rule.
* **Retry reuses the plan** — same `mediaId`, same staging key, same final key, `upsert: true`.
  Additionally `exists(finalPath)` is checked before promoting, so an attempt that moved the object
  and lost its response reuses that object instead of creating a `(2)` copy. **No code path can
  produce a second object for one logical upload.**
* **Progress** is stage-based (`queued 0 → validating .05 → staging .45 → promoting .78 →
  recording .92 → done 1`). `storage_client` 2.8.1 exposes no upload-progress callback on
  `uploadBinary`, so byte-level percentages cannot be reported honestly; the UI says so
  (`om_media_item_tile.dart:122`).

Replace/delete:

* `replace()` overwrites the existing key, keeps `id`/`storagePath`/`order`/`isPrimary`, updates the
  row, invalidates both signed-URL caches for that path.
* `delete()`/`deleteMany()` refuse a path another live ledger row claims **and** a path another
  document still embeds (the `holders` list on `media_objects`, maintained by
  `setState(... attached ...)`), which is what makes a duplicated product's shared gallery safe. A
  refusal names the document, and `deleteMany` reports what *was* deleted rather than implying the
  batch is untouched.
* `commitProductImages(product, nextImages)` is the field-level write: cap check, alt-text check,
  `FirestoreMediaGuard.ensureNoImageBytes`, `update({images: [...]})`, mark kept rows attached with
  `products/{id}` as holder, then release what fell out of the list. A refusal during that last step
  is logged, not failed — the document is already correct.

**Storefront consequence.** On a private bucket `MediaRef.url` is empty by design, so
`OmMediaImage` would render "No image". Screens must call `resolveForRender(refs, size: …)` (or
`MediaRefResolver.urlFor`) before building, and must not write the result back. On a public bucket
rendering needs no round trip.

## 8. Ledger, orphan scan and the cleanup job

`media_objects` (Firestore) is the index that says which keys are live. Shape
(`media_object_ledger.dart`):

```
{ id: <mediaId>, storagePath, bucket, kind, ownerId,
  state: 'staging' | 'attached' | 'detached',
  url?, altText, order, isPrimary,
  attachedTo: { collection, docId },        // last writer
  holders: ['products/abc', …],             // every document that embeds this object
  width?, height?, sizeBytes?, contentType,
  createdAt, updatedAt }
```

`FirestoreMediaGuard.ensureNoImageBytes` runs on every write here and on every `products.images`
write (`media_byte_guard.dart`): it rejects `Uint8List`/`ByteBuffer` values, `data:` URLs and any
≥512-character whitespace-free base64-looking string, naming the field path that broke the rule.
Other writers (catalog/order repositories) should call it too — it is a one-liner per write and the
only thing standing between an admin's hero shot and a >1 MiB document that fails to save.

**A scan never deletes anything.** `scanOrphans()` lists the bucket (paged, hard stop at
`MediaLimits.orphanScanMaxObjects` = 2000), builds the reference set from `media_objects` plus a
bounded sweep of `products`, `categories`, `reviews` and `store_settings.banners`, and returns
`OrphanScan{objects, referencedPaths, canDelete}`. `canDelete` is false — so the panel shows the
list but no delete button — whenever the sweep was partial, any document was unreadable, the ledger
is unavailable, or this device is not signed in as staff. `om_media_orphan_panel.dart` renders that
reason verbatim.

Deletion is a deliberate second step: `MediaOrphanControl.deleteConfirmed(paths)` rejects any path
the last scan did not report, re-reads the reference set, and refuses the **whole batch** if one
object became live in the meantime (a partially-applied confirmation is worse than none).

### 8.1 The scheduled janitor (server-side, needs the service-role key)

A browser sweep is a diagnostic. The real cleanup runs on a schedule with privileged credentials —
as a Firebase Function or `pg_cron` + a small worker:

1. `GET /storage/v1/object/list/om-events-media` (paginated) — every key.
2. Read `media_objects` and the four document collections; build the live key set.
3. **Delete keys under `tmp/` older than the staging TTL.** Supabase has no native object lifecycle
   rule, so this is the mechanism that keeps abandoned uploads from accumulating. Recommended:
   24 h, comfortably longer than any admin's session.
4. Report, do not delete, keys outside `tmp/` that no document and no non-`detached` row claims;
   delete them only after a human confirms (an object with a missing ledger row may still be live in
   a document written by an older build).
5. Warn on `attached` rows whose `storagePath` has no object: that is deleted-out-from-under-the-app
   and needs a product fix, not a bucket fix.

Sketch of the `pg_cron`-adjacent SQL for the bucket side, if you keep the ledger in Postgres instead:

```sql
-- run nightly; <SERVICE_ROLE_KEY> lives in Functions config, never in this file or the bundle
-- delete from storage.objects
--   where bucket_id = 'om-events-media'
--     and split_part(name, '/', 1) = 'tmp'
--     and created_at < now() - interval '24 hours';
```

## 9. Optional: server-side optimisation

Browsers in this build have no image codec dependency (no `image` package — deliberately, to keep the
bundle light), so **the client uploads the file the admin chose**. The contract for
resize/WebP/quality-strip is `MediaOptimiseGateway` (`media_optimise_gateway.dart`):

* Function name: `mediaOptimise` (`us-central1`, `FUNCTIONS_REGION` must match).
* Input: `{ stagingPath, finalPath, mediaId, bucket, kind, bytes, contentType, width, height }`.
* Output: `{ optimised: bool, finalPath?, width?, height?, bytes?, note? }`.
* It must move/rewrite the object **inside the managed prefixes**
  (`tmp`, `products`, `categories`, `banners`, `reviews`, `misc`); a returned path outside them is
  rejected with a `MediaFailure` before anything is recorded.
* It holds the Supabase service-role key; the client never sees it.

Until it is deployed, `PassthroughOptimiseGateway` is wired and the pipeline publishes the original
bytes, still bounded by the limits in §3. `CallableMediaOptimiseGateway` is ready and reports itself
disabled when Firebase is not configured, so an upload never fails because an optional step is
missing.

## 10. Limits (mirror of `MediaLimits`)

| Kind | Max bytes | Min px | Max px | Per entity |
| --- | --- | --- | --- | --- |
| product | 8 MiB | 600×600 | 5000×5000 | 10 |
| category | 6 MiB | 600×400 | 4000×4000 | 4 |
| banner | 8 MiB | 1200×400 | 5000×2500 | 6 |
| review | 5 MiB | 400×400 | 4000×4000 | 4 |
| other | 8 MiB | 200×200 | 5000×5000 | 24 |

Alt text: 3–200 characters, mandatory before upload **and** before a gallery commit. Formats: JPEG,
PNG, WebP, AVIF (AVIF whose dimensions cannot be read is accepted with an `approximate` note; a
truncated JPEG/PNG/WebP is refused). Signed URL TTL 15 min, refresh margin 3 min. Delete batches
50. Ledger sweep 5000 documents/collection, bucket sweep 2000 objects.

## 11. Go-live checklist

1. [ ] Bucket `om-events-media` created, transformations on, 8 MiB cap, 4 MIME types.
2. [ ] Policies §4 applied; `<STAFF_ROLE_CLAIM>` chosen and staff JWTs actually carry it.
3. [ ] Anonymous sign-ins enabled, **or** Firebase→Supabase token exchange live (§4.1).
4. [ ] `SUPABASE_URL` / `SUPABASE_ANON_KEY` / `SUPABASE_MEDIA_BUCKET` supplied via `--dart-define`;
   `Env.hasServiceRoleKeyInClient` is false in the release bundle.
5. [ ] Firestore rules allow authenticated writes to `media_objects` and staff reads of `products`,
   `categories`, `reviews`, `store_settings` (the orphan sweep needs all four).
6. [ ] Admin → Media: upload one product image, watch the stages, reload the product, confirm the
   object is at `products/{slug}/000-{mediaId}.jpg` and the row reads `attached`.
7. [ ] Replace it: same key, no `(2)` object, admin note about the 24 h CDN window.
8. [ ] Cancel mid-upload: `tmp/` copy gone, row `detached`, no document changed.
9. [ ] Run a scan on a bucket with a hand-deleted object: candidates listed, delete disabled until
   the scan is complete, then confirm exactly one path and check the row and object both go.
10. [ ] Unconfigured smoke test: build with no `SUPABASE_*` defines, confirm every upload control is
    disabled with the message naming the missing keys, and that nothing reports success.
11. [ ] Scheduled cleanup job (§8.1) deployed, with the `tmp/` age rule enabled.
